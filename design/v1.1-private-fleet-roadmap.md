# Formal Product Spec: V1.1 Private Fleet Harness

**Status:** accepted directional baseline
**Date:** 2026-05-17
**Scope:** private production-readiness, cascading upgrades, process-domain breadth, and real-repo dogfood
**Relationship to v1:** extends the v1 closeout baseline; deprioritizes public distribution

This document defines the next product milestone after v1 local-tarball
closeout.

V1 proved that the harness can be packaged, installed, validated, extended with
modules, and planned for upgrades. V1.1 shifts the product center from
distribution readiness to practical private use across a set of real repos.

The public-package path remains useful as validation machinery, but it is not
the product goal for this milestone.

## Product Intent

Build a practical, durable, portable harness that Julie can install across her
own repos without hand-setting the same agent rules, workflows, files,
commands, and process-domain scaffolds in each repo.

The core harness repo should remain the improvement source. When the core repo
adds better modules, templates, validations, workflow rules, or lifecycle
behavior, installed target repos should be able to inspect, plan, and safely
receive those improvements.

The harness should optimize two loops at the same time:

1. Improve the process domains in the core repo through dogfood.
2. Cascade useful improvements into already-initialized project repos.

Portable means installable and maintainable across different repo shapes. It
does not mean public-facing, public-registry-first, or generalized for unknown
users before it is effective for the private repo set.

## Versioning

Use **v1.1** as the product milestone name.

The npm package version does not need to move in lockstep with this document.
The package can remain private and use `0.1.x` versions until the cascade
upgrade flow itself needs stronger package-version semantics.

For this milestone:

- `v1` means the closed local-tarball install and validation baseline.
- `v1.1` means private production readiness across the source repo and real
  target repos.
- Public npm release is explicitly deferred unless a later decision reopens it.

## V1.1 Outcome

V1.1 is successful when the harness can maintain a small private fleet of target
repos from the core repo with minimal manual setup.

Success means:

- Target repos can be registered, inspected, and reported as a known private
  target set.
- The core repo can inspect installed harness state across registered targets.
- Profile changes can be planned and applied safely.
- Core module/profile/template improvements can be planned against installed
  targets.
- Safe changes can cascade automatically; review-required changes are surfaced
  clearly and do not mutate targets.
- Every formal v1 harness process domain has at least a baseline installed
  artifact, command, validation, or explicit integration path.
- The harness is dogfooded on itself and exercised against real repos rather
  than only temp fixtures.
- The operator no longer needs to hand-copy the same operating rules and
  workflow scaffolds into each repo.

## Product Principles

- **Private utility first:** optimize for Julie's real repos before optimizing
  for unknown external users.
- **Cascade improvements:** core repo improvements should become inspectable
  and applicable to existing target installs.
- **Plan before mutate:** target repos should get explicit plans, safe/review
  classification, and refusal on blocked work.
- **Real-repo pressure:** every major lifecycle improvement should be exercised
  against the harness repo and at least one named target repo.
- **Process domains must become usable:** do not add a domain only as prose.
  Each domain needs artifacts, commands, validation, or dogfood behavior.
- **Local specificity is allowed:** target repos may have repo-specific
  context, workflows, and overrides. The harness should preserve those
  differences while keeping common workflow infrastructure maintainable.
- **Distribution is supporting infrastructure:** packed-package smoke remains
  valuable because it proves portability, but public registry release is not a
  v1.1 priority.

## Non-Goals

- Public npm publication.
- Public marketing, external docs polish, or a public support posture.
- Homebrew, standalone binary, or alternate public distribution channels.
- Fully automatic conflict resolution for human-authored files.
- A dashboard or hosted service.
- LLM-provider-specific integrations.
- Replacing repo-specific human judgment with global policy.

## Current Baseline

Already built:

- `harness init --profile <profile>`
- `harness doctor`
- `harness modules list`
- `harness modules add <module>`
- `harness profiles list`
- `harness profiles inspect <profile>`
- `harness lock refresh`
- `harness lock check`
- `harness upgrade --plan`
- `harness upgrade apply` for limited safe operations
- structured metadata, canonical state, invariants, plans/status, decisions,
  questions, package validation, external smoke, and named `meetingly` smoke

Already dogfooded:

- the source repo as the `dogfood` profile target
- `~/code/meetingly` as a copied external smoke target for `minimal` and
  `dogfood`

Known gaps:

- no persistent private target registry
- no profile switching command
- no fleet-wide upgrade planning or safe cascade apply
- no full human-facing file/template upgrade workflow
- no baseline modules for Durable Memory, Capture And Triage, Application /
  Corpus Legibility, Reconciliation And Drift Detection, Gardening And Entropy
  Management, or Reports And Retrieval

## V1.1 Roadmap

### Phase 1: Private Target Registry

Purpose:

- Make installed target repos first-class local state.
- Stop treating real-repo dogfood as ad hoc command history.

Candidate artifact:

- `targets/repos.yaml`

Candidate commands:

- `harness targets list`
- `harness targets check`
- `harness targets inspect <target-id>`
- `harness targets report`

Initial target record fields:

- `id`
- `path`
- `purpose`
- `status`
- `desired_profile`
- `installed_profile`
- `install_source`
- `last_validated`
- `notes`

Exit signal:

- The harness repo and at least one real repo are represented in a target
  registry.
- `doctor` validates the registry shape.
- `targets inspect` can run harness inspection commands against registered
  targets without mutating them.
- The registry is dogfooded in this repo and validated in tests.

### Phase 2: Profile Switching And Profile Sync

Purpose:

- Let an initialized target move from one profile to another without manual
  manifest edits.
- Build on `profiles inspect` so switching is plan-first.

Candidate commands:

- `harness profiles switch <profile> --target <path> --plan`
- `harness profiles switch <profile> --target <path> --apply`
- `harness profiles sync --target <path> --plan`

Initial behavior:

- Install clean missing modules required by the requested profile.
- Update target manifest profile only after required modules are installed.
- Refuse artifact or command collisions unless a future merge policy explicitly
  handles them.
- Do not remove modules by default when switching to a smaller profile.

Exit signal:

- A minimal target can switch to dogfood through a plan-first command.
- Switch behavior is covered in temp targets and at least one copied real repo.

### Phase 3: Cascade Upgrade Planning

Purpose:

- Make core improvements inspectable across already-initialized repos.

Candidate commands:

- `harness targets upgrade --plan`
- `harness targets upgrade --apply-safe`
- `harness targets upgrade --target <target-id> --plan`

Initial behavior:

- Run upgrade planning across the target registry.
- Summarize safe, review-required, blocked, and deferred operations per target.
- Apply only safe operations.
- Preserve target-specific human-authored differences.

Exit signal:

- A core module/profile improvement can be planned against all registered
  targets.
- Safe changes can cascade into copied test targets and then an approved real
  target.

### Phase 4: Remaining Domain Baselines

Purpose:

- Bring every formal v1 process domain into at least baseline operational
  coverage.

Candidate module order:

1. Durable Memory
2. Capture And Triage
3. Application / Corpus Legibility
4. Reports And Retrieval
5. Reconciliation And Drift Detection
6. Gardening And Entropy Management

Order rationale:

- Durable Memory and Capture And Triage improve day-to-day agent continuity.
- Application / Corpus Legibility makes real repo work safer.
- Reports And Retrieval turns growing state into usable summaries.
- Reconciliation and Gardening become more valuable after more state exists.

Exit signal:

- Each remaining domain has an installable module or an explicit integration in
  an existing module.
- Each domain has at least one validation path and one dogfood use.

### Phase 5: Private Production Hardening

Purpose:

- Make the harness robust enough to trust across active project repos.

Candidate work:

- Better error messages and remediation hints.
- Backups or snapshots before mutating target repos.
- More real-repo smoke targets.
- Downgrade or rollback planning for failed safe applies.
- Documentation for private repo rollout.
- Compatibility checks for repos with existing agent instructions.

Exit signal:

- The harness can manage several active private repos without manual setup
  drift.
- Core improvements can be rolled out deliberately and safely.
- Public publication remains optional rather than required.

## Recommended Next Build Step

Build the **Private Target Registry** first.

Profile switching is still important, but the target registry should come
first because it creates the durable map of where the harness is installed and
where future improvements must cascade. Without that map, switching and upgrade
work remains target-by-target and ad hoc.

The first target-registry increment should be intentionally narrow:

1. Add `targets/repos.yaml`.
2. Add `harness targets list`.
3. Add `harness targets check`.
4. Add `harness targets inspect <target-id>` as read-only orchestration over
   existing `doctor`, `profiles inspect`, and `upgrade --plan` behavior.
5. Register the harness repo and `meetingly` as the first named private target
   evidence.

Only after that should v1.1 move to profile switching.

## Validation Expectations

Every v1.1 increment should preserve the v1 closeout baseline and add focused
validation for the new behavior.

Minimum validation for v1.1 lifecycle changes:

```bash
npm test
npm run doctor
npm run lock:check
npm run metadata:check
npm run state:check
npm run plans:check
npm run upgrade:plan
npm run profiles:inspect -- dogfood
git diff --check
```

When target-registry or cascade behavior changes, also validate against copied
real targets before mutating any real target directly.

## Sequencing Rules

1. Prefer private repo usefulness over public distribution work.
2. Prefer improvements that make existing target installs easier to inspect,
   upgrade, or validate.
3. Add process-domain breadth only when it creates executable behavior.
4. Dogfood every increment in the harness repo.
5. Exercise lifecycle changes against at least one named real repo copy.
6. Keep safe/review/blocked classifications explicit before applying changes.
7. Do not reopen public publication unless a new decision explicitly changes
   the v1.1 priority.
