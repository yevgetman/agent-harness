# Formal Product Spec: V1.1 Installed Instance Harness

**Status:** accepted directional baseline
**Date:** 2026-05-17
**Scope:** standalone tool behavior, installed-repo upgrades, process-domain breadth, and real-repo dogfood
**Relationship to v1:** extends the v1 closeout baseline; rejects central target-registry control

This document defines the next product milestone after v1 local-tarball
closeout.

V1 proved that the harness can be packaged, installed, validated, extended with
modules, and planned for upgrades. V1.1 shifts the product center from
distribution readiness to practical installed-instance behavior.

The harness source repo is a standalone codebase that defines the harness tool.
It is not a command center and should not maintain a registry of repos where
the harness is installed.

## Product Intent

Build a practical, durable, portable harness tool that Julie can install into
her own repos without hand-setting the same agent rules, workflows, files,
commands, and process-domain scaffolds in each repo.

Each target repo owns its installed harness state locally. The source repo owns
the harness code, module definitions, templates, validation behavior, and
upgrade logic.

When the harness source improves, each installed repo should be able to run its
own upgrade process and receive those improvements through an explicit
plan-first workflow.

The harness should optimize two loops at the same time:

1. Improve the process domains and lifecycle behavior in the source repo
   through dogfood.
2. Let each installed repo independently inspect, plan, and apply compatible
   upgrades from the current harness tool version.

This is closer to a CLI installation model than a central control-plane model:
installing the tool does not make the source repo know where the tool is
installed.

## Versioning

Use **v1.1** as the product milestone name.

The npm package version does not need to move in lockstep with this document.
The package can remain private and use `0.1.x` versions until installed-repo
upgrade behavior needs stronger package-version semantics.

For this milestone:

- `v1` means the closed local-tarball install and validation baseline.
- `v1.1` means production-ready installed-instance behavior for private use.
- Public npm release is explicitly deferred unless a later decision reopens it.

## Architecture Boundary

The source repo should know:

- harness source code
- module and profile definitions
- templates and generated artifacts
- validation rules
- upgrade planning and apply logic
- package/build behavior

The source repo should not know:

- which repos have installed the harness
- where target repos live locally
- each target repo's live harness status
- whether a specific target has upgraded

Each installed target repo should know:

- its local `.harness/manifest.yaml`
- its local `.harness/lock.yaml`
- its installed profile and modules
- its harness-managed files
- its configured package/source/version channel when applicable
- its local repo-specific context and overrides

Each installed target repo should not need to know:

- the source checkout path
- other repos that have the harness installed
- a central registry in the source repo

## V1.1 Outcome

V1.1 is successful when an initialized repo can behave like a durable installed
instance of the harness.

Success means:

- A repo can install the harness and keep its own local harness state.
- A repo can inspect its installed state and active profile.
- A repo can plan upgrades from the currently executing harness tool version.
- A repo can apply safe compatible upgrades without central coordination.
- Review-required and blocked upgrades are surfaced clearly and do not mutate
  the repo.
- Profile changes can be planned and applied inside the target repo.
- Core module/profile/template improvements can cascade by running upgrade
  commands in individual installed repos.
- Every formal v1 harness process domain has at least a baseline installed
  artifact, command, validation, or explicit integration path.
- Real repo dogfood proves installed-instance behavior without creating a
  source-owned target registry.

## Product Principles

- **Installed repo autonomy:** each repo owns its local harness installation and
  upgrade decisions.
- **No central target registry:** the source repo defines the tool; it does not
  track where the tool is installed.
- **Cascade through the tool:** improvements cascade when an installed repo
  runs the upgraded harness tool against itself.
- **Plan before mutate:** installed repos should get explicit plans,
  safe/review/blocked classification, and refusal on blocked work.
- **Private utility first:** optimize for Julie's real repos before optimizing
  for unknown external users.
- **Process domains must become usable:** do not add a domain only as prose.
  Each domain needs artifacts, commands, validation, or dogfood behavior.
- **Local specificity is allowed:** target repos may have repo-specific
  context, workflows, and overrides. The harness should preserve those
  differences while keeping common workflow infrastructure maintainable.
- **Distribution is supporting infrastructure:** packed-package smoke remains
  valuable because it proves portability, but public registry release is not a
  v1.1 priority.

## Non-Goals

- A source-owned registry of installed target repos.
- Central command-center behavior.
- Fleet-wide orchestration from the source repo.
- Public npm publication.
- Public marketing, external docs polish, or a public support posture.
- Homebrew, standalone binary, or alternate public distribution channels.
- Fully automatic conflict resolution for human-authored files.
- A dashboard or hosted service.
- LLM-provider-specific integrations.
- Replacing repo-specific human judgment with global policy.

Phase 1 installed-instance upgrade contract is implemented at a narrow
baseline:

- manifests distinguish installed-instance source metadata from central
  registration
- package-installed targets record package source, lifecycle channel, and npm
  registry tag
- source-checkout dogfood records local source and lifecycle channel
- upgrade plans report repo-local source/channel guidance and next operator
  action
- private per-repo upgrade flow is documented

Phase 2 profile switching and sync has plan and clean apply increments:

- switch plans reuse profile inspection and module-add preflight
- clean missing requested-profile modules are planned as safe installs
- collisions are review-required and unavailable modules are blocked
- profile updates are planned only after required modules are installed or
  cleanly installable
- modules outside a smaller requested profile are retained by default
- clean switch applies re-run the plan, pre-check installs, install required
  modules, update the manifest profile last, refresh lock provenance, and
  refuse review-required or blocked operations
- sync plans read the target's active manifest profile, report installed and
  missing active-profile modules, classify collisions, and retain modules
  outside the active profile without switching profiles
- clean sync applies re-run the plan, pre-check installs, install missing
  active-profile modules, retain modules outside the active profile, and never
  switch the target manifest profile

## V1.1 Roadmap

### Phase 1: Installed-Instance Upgrade Contract

Purpose:

- Make each target repo's upgrade path explicit and independent.
- Define how an installed repo receives core harness improvements without the
  source repo tracking target locations.

Candidate work:

- Clarify manifest source/channel fields for installed repos.
- Add upgrade-plan output that explains where the executing harness version
  came from and how the target can update.
- Ensure package-installed and source-checkout dogfood paths behave
  consistently.
- Add docs for the operator flow: update/build/install the harness tool, then
  run upgrade plan/apply inside a target repo.

Exit signal:

- A target repo can answer "what harness instance am I running, what source
  channel is it using, and what upgrades would this tool apply here?"
- The source repo does not need to know that target repo exists.

### Phase 2: Profile Switching And Profile Sync

Purpose:

- Let an initialized target move from one profile to another without manual
  manifest edits.
- Build on `profiles inspect` so switching is plan-first.

Candidate commands:

- `harness profiles switch <profile> --plan`
- `harness profiles switch <profile> --apply`
- `harness profiles sync --plan`
- `harness profiles sync --apply`

Initial behavior:

- Default target is the current working repo.
- Install clean missing modules required by the requested profile when
  switching.
- Plan clean missing modules required by the active profile when syncing.
- Update target manifest profile only after required modules are installed.
- Refuse artifact or command collisions unless a future merge policy explicitly
  handles them.
- Do not remove modules by default when switching to a smaller profile.

First increment exit signal:

- A minimal target can switch to full through a plan-first command.
- Switch behavior is covered in temp targets.

Full phase exit signal:

- A minimal target can apply a switch to full through a plan-first command.
- A target can plan whether its active manifest profile is satisfied without
  switching profiles.
- A target can apply clean active-profile alignment without switching profiles.
- Switch and sync behavior are covered in temp targets and at least one copied
  real repo.

### Phase 3: Cascading Upgrade Apply For Installed Repos

Purpose:

- Make core improvements applicable by running the upgraded harness tool inside
  each installed repo.

Candidate commands:

- `harness upgrade --plan`
- `harness upgrade apply`
- future narrow apply subcommands for review-mediated template updates

Initial behavior:

- Keep upgrade planning repo-local.
- Summarize safe, review-required, blocked, and deferred operations.
- Apply only safe operations.
- Preserve target-specific human-authored differences.
- Make review-required human-facing file/template changes explicit and
  inspectable.

Exit signal:

- A core module/profile/template improvement can be planned inside an installed
  target repo.
- Safe changes can apply in copied test targets and then in an approved real
  target.

### Phase 4: Remaining Domain Baselines

Purpose:

- Bring every formal v1 process domain into at least baseline operational
  coverage.

Candidate module order:

1. Durable Memory — implemented baseline
2. Capture And Triage — implemented baseline
3. Application / Corpus Legibility — implemented baseline
4. Reports And Retrieval — implemented baseline
5. Reconciliation And Drift Detection — implemented baseline
6. Gardening And Entropy Management — implemented baseline

Order rationale:

- Durable Memory and Capture And Triage improve day-to-day agent continuity.
- Application / Corpus Legibility makes real repo work safer.
- Reports And Retrieval turns growing state into usable summaries.
- Reconciliation and Gardening become more valuable after more state exists.

Exit signal:

- Each remaining domain has an installable module or an explicit integration in
  an existing module.
- Each domain has at least one validation path and one dogfood use.

### Phase 5: Private Production Hardening

Purpose:

- Make the harness robust enough to trust across active project repos.

Candidate work:

- Better error messages and remediation hints.
- Backups or snapshots before mutating target repos — implemented baseline.
- More copied real-repo smoke targets.
- Rollback planning for failed safe applies.
- Documentation for private repo rollout.
- Compatibility checks for repos with existing agent instructions.

Exit signal:

- The harness can be installed and upgraded in several active private repos
  without manual setup drift.
- Core improvements can be rolled out deliberately by running upgrade commands
  in individual installed repos.
- Public publication remains optional rather than required.

## Recommended Next Build Step

The **Installed-Instance Upgrade Contract** exists at a narrow baseline.

It was the right first v1.1 step because it protects the architecture boundary:
the source repo defines upgrade behavior without knowing where it is installed.

The completed upgrade-contract increment:

1. Clarifies installed manifest source/channel semantics.
2. Makes `harness upgrade --plan` report installed-instance upgrade source and
   next operator action explicitly.
3. Documents the private operator workflow for updating the harness tool and
   then running upgrade plan/apply inside a target repo.
4. Validates the behavior in this dogfood repo and copied real repos through
   tests and smoke checks.

The first cascade apply baseline now exists for clean module-template
managed-file updates. Profile sync planning and clean apply now exist for
active-profile alignment checks. Durable Memory, Capture And Triage,
Application / Corpus Legibility, Reports And Retrieval, Reconciliation And
Drift Detection, and Gardening And Entropy Management now have baseline
coverage. The first Gardening depth pass also exists: `harness garden plan`
uses configurable thresholds, reports read-only action policy, labels reviewed
cleanup actions, and runs during full-profile smoke validation. Lifecycle
backups now exist before supported mutation surfaces and write local backup
manifests under `.harness/backups/` or `.harness-destroy-backups/`. Rollback
planning now uses those manifests to inspect recovery state without mutating
files.

The next recommended build step is private production hardening for
review-mediated upgrade workflows: broaden generated-file, module-definition,
semantic YAML merge, or reviewed file/template update behavior while
preserving the safe/review/blocked boundary. This is the right move because
installed repos can now install, switch, sync, back up, inspect recovery state,
and apply clean lifecycle changes; the remaining practical gap is helping
operators review and apply non-clean upgrade work without manual drift.
Rollback restore/apply should wait until plan-only rollback has dogfood
evidence.

## Validation Expectations

Every v1.1 increment should preserve the v1 closeout baseline and add focused
validation for the new behavior.

Minimum validation for v1.1 lifecycle changes:

```bash
npm test
node --check scripts/lifecycle-backup.mjs
node --check scripts/rollback.mjs
npm run doctor
npm run lock:check
npm run metadata:check
npm run state:check
npm run plans:check
npm run capture:check
npm run legibility:check
npm run reports:check
npm run reconcile:check
npm run reconcile:plan
npm run garden:check
npm run garden:plan
npm run memory:check
npm run upgrade:plan
npm run profiles:inspect -- full
npm run distribution:smoke
npm run distribution:global-smoke
git diff --check
```

When installed-instance upgrade behavior changes, validate against copied real
targets before mutating any real target directly.

## Sequencing Rules

1. Prefer installed-repo usefulness over public distribution work.
2. Preserve the boundary that the source repo does not track installations.
3. Prefer improvements that make an installed repo easier to inspect, upgrade,
   or validate locally.
4. Add process-domain breadth only when it creates executable behavior.
5. Dogfood every increment in the harness repo.
6. Exercise lifecycle changes against at least one copied real repo.
7. Keep safe/review/blocked classifications explicit before applying changes.
8. Do not reopen public publication unless a new decision explicitly changes
   the v1.1 priority.
